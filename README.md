# LLM Lead Scoring Experiment

This repository contains the data, prompts, experiment code, model-selection and prompt-calibration materials, preprocessing steps, and statistical analyses for a controlled study of LLM-based B2B lead scoring. The study examines how large language models respond to isolated changes in synthetic lead features and whether their generated explanations reflect those changes.

## Research Objective

The experiment evaluates the consistency and traceability of observable LLM behavior in lead scoring tasks. It does **not** evaluate predictive accuracy against actual purchases or conversions because the synthetic experiment has no external ground-truth outcomes.

The analyses address four areas:

- **H1 — Feature sensitivity:** Whether changes in behavioral features are more likely to alter the lead classification than changes in firmographic features.
- **H2 — Stability:** Whether repeated outputs vary when the model, prompt, and lead profile are identical.
- **H3 — Explanation alignment:** Whether the experimentally manipulated feature is cited as a contributing factor in the model's self-explanation.
- **H4 — Model differences:** Whether classifications, perturbation responses, stability, and explanations differ across the selected LLMs.

The primary outputs are:

1. a binary classification: `High intent` or `Low intent`; and
2. a short free-text explanation returned in a structured JSON response.

Self-explanations are treated as observable textual outputs, not as faithful representations of a model's internal reasoning.

## Experimental Design (OFAT)

The study uses a controlled **one-factor-at-a-time (OFAT)** perturbation design. For each experimental condition, exactly one lead feature is changed while the remaining features and experimental settings are held constant. The resulting minimal pairs make it possible to attribute observed output differences to the manipulated feature within the limits of the design.

The sample is based on five synthetic reference profiles representing different B2B lead scenarios. For each profile, the experiment includes one baseline and twelve perturbations: each of six features is independently set to a predefined low or high boundary value.

```text
1 baseline + (6 features × 2 perturbation levels) = 13 conditions per profile

5 profiles × 13 conditions × 5 repeated runs × 3 models = 975 model outputs
```

The 975 API calls are randomized across profiles, conditions, runs, and models. The order of the six features inside the prompt remains fixed. The OFAT design estimates the effects of individual feature changes; feature interactions are outside the scope of this study.

## Variables

### Firmographic features

The static company attributes are:

- `company_size` — number of employees;
- `industry` — the organization's industry; and
- `region` — the organization's geographic market.

### Behavioral features

The behavior-based attributes are:

- `dwell_time` — cumulative time spent on the vendor's website;
- `demo_requests` — number of requested product demonstrations; and
- `email_response` — the response to an outbound contact attempt.

The behavioral features describe interactions attributed to a prospective organization in the experimental scenario. They do not describe the characteristics of a real person.

> **Data privacy:** All lead profiles and input data in this repository are synthetic. The repository contains no real leads, customer records, or personal data.

### Dependent variables

- **Lead score:** Binary classification as `High intent` or `Low intent`.
- **Self-explanation:** Short free-text justification generated by the model.

### Controlled conditions

The main experiment holds the following conditions constant:

- prompt wording and structure;
- vendor context;
- order of the six input features; and
- model parameter configuration, including `temperature = 0`.

Temperature zero reduces sampling-related variation but does not guarantee identical outputs across repeated API calls.

## Models, Runs, and Prompt Calibration

The main experiment compares three instruction-tuned models accessed through the GWDG Chat AI API:

- Meta Llama 3.1 8B Instruct;
- Apertus 70B Instruct; and
- OpenAI GPT-OSS 120B.

Each model processes every experimental condition five times. The repeated runs support the stability analyses and are treated as repeated realizations of the same model under identical input conditions.

Before the main experiment, eligible models were screened for technical suitability, including availability, latency, error rates, and valid structured output. Prompt calibration compared five prompt variants using Meta Llama 3.1 8B Instruct. The selected variant was then frozen and used unchanged for all three models to avoid model-specific prompt optimization as a confounding factor.

The production prompt consists of:

1. a fixed vendor context describing a European B2B IT consulting provider;
2. the binary lead-classification task; and
3. a structured lead profile containing the six features.

No explicit scoring rules, feature weights, or numerical decision thresholds are provided to the models.

## Data Collection and Processing

The main experiment was executed serially through the GWDG Chat AI API. Failed calls were retried using exponential backoff, and completed observations were stored through checkpointing so that interrupted collection could resume without duplicating successful calls.

For every model call, the experiment records the binary score, complete self-explanation, and analysis metadata such as the model, run number, case ID, profile ID, manipulated feature, and perturbation level.

The preprocessing workflow extracts and cleans the structured responses. The explanation-coding workflow maps each perturbation explanation to one of four nominal categories based on the role of the manipulated feature:

| Code | Category | Meaning |
|---:|---|---|
| 0 | Not specified | The manipulated feature is not mentioned or clearly described. |
| 1 | Specified, neutral | The feature is mentioned but is not attributed an effect on the outcome. |
| 2 | Specified, refuted | The feature is acknowledged but explicitly outweighed by other factors. |
| 3 | Supportive, explanatory | The feature is cited as contributing to the classification. |

Baseline observations are not assigned an explanation-alignment code because no feature is manipulated in a baseline condition. Algorithmic pre-coding serves as a review aid; the final coding decisions are based on the documented coding rules.

## Statistical Analysis Overview

The analysis is organized by hypothesis:

- **H1:** Matched low/high perturbations, binary sensitivity indicators, and a logistic generalized estimating equation (GEE), with model as a fixed effect and robust standard errors. Supplementary analyses include baseline-anchored changes, directionality, feature-level summaries, and leave-one-profile-out checks.
- **H2:** Krippendorff's alpha, complete agreement, modal agreement share, and case-level instability for repeated lead scores and explanation codes.
- **H3:** Case-level alignment shares and complete-alignment rates, primarily for perturbations whose majority classification differs from the corresponding baseline majority; a broader analysis includes all perturbations.
- **H4:** Matched model comparisons using Bayesian logistic mixed models, Friedman tests, and paired Wilcoxon tests as appropriate. Confirmatory pairwise comparisons are conducted only after a significant omnibus model effect.

The nominal significance level is `α = .05`. Holm correction is applied within predefined multiple-testing families. Exploratory analyses are labeled separately and are not used as confirmatory hypothesis tests.

## Replication Instructions

### Prerequisites

You will need:

- Git;
- a compatible Python 3 environment;
- the Python dependencies imported by the experiment and analysis scripts; and
- valid credentials and access to the configured model API if you intend to rerun model inference.

### Required execution order

Run the workflow from the repository root in the following order:

1. **Clone the repository and select the documented version.**

   ```bash
   git clone https://github.com/rosaliekripp/llm-lead-scoring-experiment
   cd llm-lead-scoring-experiment
   git checkout <RELEASE_TAG_OR_COMMIT>
   ```

2. **Create and activate an isolated Python environment.**

   Creating a virtual environment is recommended to avoid dependency conflicts.

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   ```

   On Windows PowerShell:

   ```powershell
   .venv\Scripts\Activate.ps1
   ```

3. **Install the repository's dependencies.**

   ```bash
   python3 -m pip install --upgrade pip
   python3 -m pip install -r requirements.txt
   ```

4. **Review the data and experiment documentation.**

   Read:

   - `01_data/README.md`;
   - `02_experiment/README.md`; and
   - `03_analysis/README.md`.

5. **Review the frozen experiment inputs.**

   Confirm the synthetic profiles and inspect:

   - `01_data/synthetic/synthetic_lead_profiles.csv`;
   - `02_experiment/system_prompt.txt`; and
   - `02_experiment/user_prompt.txt`.

6. **Configure API access only if rerunning inference.**

   Create a local `.env` file in the repository root and add the required API credentials:

   ```env
   API_KEY=your_api_key_here
   BASE_URL=your_base_url_here
   ```

   The experiment scripts load the credentials from this file. Alternatively, define the same variable directly in your local environment. 
   
   Never commit the `.env` file, or insert API keys, access tokens, or other credentials directly into source files.

7. **Optionally validate one case before the full run.**

   ```bash
   python3 02_experiment/run_single_case.py
   ```

   Use the script-specific options documented in `02_experiment/README.md`.

8. **Run the full experiment, or use the archived results.**

   ```bash
   python3 02_experiment/run_full_experiment.py
   ```

   The checkpoint file supports resuming an interrupted run. Do not delete or overwrite archived result files unless you intentionally want to replace them. To reproduce only the reported analyses, skip model inference and use the archived result files in `02_experiment/results/`.

9. **Run preprocessing in this order.**

   ```bash
   python3 03_analysis/preprocessing/clean_results.py
   python3 03_analysis/preprocessing/explanation_coding_scheme.py
   ```

   The coding workflow may include a documented manual-review step. Preserve both algorithmic suggestions and final reviewed codes where provided.

10. **Run the hypothesis-specific analyses in this order.**

    ```text
    03_analysis/h1/
    03_analysis/h2/
    03_analysis/h3/
    03_analysis/h4/
    ```

    Execute the scripts inside each directory according to `03_analysis/README.md` and any folder-level documentation. Run `03_analysis/h1_x/` only after the primary H1–H4 analyses because it contains exploratory cross-hypothesis analyses.

11. **Compare regenerated outputs with the archived results.**

    Confirm row counts, identifiers, preprocessing outputs, analysis tables, and figures before interpreting differences.

## Reproducibility Notes

The result files included in this repository are the outputs used for the reported analyses. Re-running the model calls may not produce byte-identical results, even with `temperature = 0`, because provider infrastructure, model versions, serving implementations, or other nondeterministic processes may change over time.

For the closest possible reproduction:

- use the release or commit associated with the study;
- retain the archived prompts and synthetic inputs unchanged;
- use the documented model identifiers and API configuration;
- preserve the randomized execution plan or random seed where documented;
- do not modify the archived raw results before preprocessing; and
- record the execution date, model endpoint, dependency versions, and any deviations from the original procedure.

The archived results should be used to reproduce the published preprocessing and statistical analyses. A fresh inference run should be treated as a replication run and compared with, rather than silently substituted for, the archived data.

## Scope and Limitations

- The synthetic setup supports controlled comparisons but does not establish real-world conversion accuracy.
- The experiment covers six predefined features, five reference profiles, and three selected models; findings should not be generalized automatically to all lead attributes, customer populations, or LLMs.
- The OFAT design identifies responses to individual feature changes but does not estimate interactions between features.
- Generated explanations are analyzed as outputs and should not be interpreted as direct access to hidden model reasoning.
- The terms *low* and *high* for categorical perturbations refer only to predefined suitability within the experimental vendor context; they do not imply an intrinsic ranking of industries or regions.
